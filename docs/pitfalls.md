# 工程排坑指南 (Pitfalls & Best Practices)

在处理大量中文工程标准、会议纪要、设计图纸与招投标文件的实际转换过程中，我们沉淀了以下 23 条关键排坑经验：

---

### 坑 1：先分类再选引擎，谨防“静默成功”
- **现象**：使用轻量文本提取工具处理纯扫描件 PDF 时，进程退出码为 0，看似转换成功，但生成的 Markdown 文件大小为 0 字节，或者只包含空空如也的换行。
- **正解**：前置运行分类探测脚本，先查看文本层字符密度。无有效文本层时直接切入 OCR/版面模型。

### 坑 2：中文 OCR 的固有形近字风险
- **现象**：无论多先进的轻量 OCR（如 EasyOCR、PaddleOCR 通用模型），在中文专业词汇中均存在结构性易错字：
  - 「主变电所」误识为「主娈电所」
  - 「出入口」误识为「出人口」
  - 「通信网络」误识为「通信网终」
  - 「一般规定」误识为「般规定」
- **对策**：对重要标准规范、关键技术规格书，关键数值与专有名词不可完全盲信通用轻量 OCR。优先采用带文本层的原稿（走 fast 模式）；若是扫描件，需使用高精度视觉版面模型（如 MinerU）并配合专有名词词典校验。
- **工具**：`tools/qa_check.py` 内置常见误识词表（`fix` 级可 `--fix` 自动替换，`review` 级只提示），并支持 `--dict` 追加本单位的专有名词 TSV；`--against` 可与另一版本逐个比对数字。

### 坑 3：矢量图纸 PDF 的“假文本层”陷阱
- **现象**：图纸 PDF 提取出的字符量往往有 1000~1600 字，但全是图框、会签栏（设计、审核、审定、图号、比例尺）。图纸正文的主体内容实际上是矢量线条与符号。
- **对策**：若正文有效自然段极少，判定为工程图纸，必须走版面模型提取图表，或交由 Vision 多模态模型结合坐标进行理解。
- **注意反向误判**：只数关键词是不够的——"设计、审核、日期、专业、阶段"在**设计规范正文**里几乎每页都有，单靠全页关键词计数会把规范误判为图纸。应当只看**图签所在位置**（右下角/右侧竖条，注意 `/Rotate` 旋转页）的**强特征词**（图号、图名、比例、审定、校核、会签……），再结合图幅与矢量路径数计分。详见 [routing-rules.md §2.3](routing-rules.md)。

### 坑 4：语音/会议转写稿 PDF 的水印与断行污染
- **现象 1（水印行）**：录音整理稿常在正文段落之间夹杂整行水印，例如 `张工(012345)某某公司 2026-10-25 10:35:18`。
- **对策 1**：不要单单替换人名，应当整行剔除——但**只匹配"整行就是水印"的短行**。早期版本的正则 `^.*?\(\d+\).*?日期 时间.*?$` 过宽，会把「(1) 2026-11-04 14:00:00 召开评审会，投资 98.6 亿元。」这样的正文整行删掉。改进后的要点：
  - 行长度上限（≤80 字符），且时间戳必须在**行尾**；
  - 姓名/单位部分不允许出现句读标点；
  - 兼容全角括号 `（）` 与 `-`、`/`、`.`、`年月日` 等日期分隔符。
- **现象 2（双栏排版硬断行与半角空格）**：原本连贯的一句话因为排版宽度被截断，且中文字符之间夹杂大量空格（例如 `“该 技 术 规 格 书”`）。
- **对策 2**：只剔除中文字符之间的**水平空白**。注意不要用 `\s`——它包含换行符，会把标题和下一段正文粘成一行：
  ```python
  HSPACE = r"[ \t\u00a0\u3000]"
  text = re.sub(rf"(?<=[\u4e00-\u9fff，。、；：？！）】》”]){HSPACE}{{1,3}}(?=[\u4e00-\u9fff])", "", line)
  ```
  「第一章 总则」「附录A 名词解释」这类标题前缀后的空格应保留。硬换行合并要单独做，并且遇到新条目编号（`3.1.2`、`（1）`、`第三章`）或短标题时不合并。
- **关键约束**：清洗后务必抽检关键数字、百分比与度量衡单位，确保正则没有误伤关键技术参数。
- **工具**：`tools/clean_transcript.py` 实现了以上全部规则，自动比对清洗前后的数字序列（`--strict` 时校验失败返回非零退出码），`--report` 输出被删行供人工复核。

### 坑 5：嵌套列表层级扁平化
- **现象**：某些快速流式抽取工具遇到多级列表时，会报 `List without detected level`，直接将二级、三级条目一律扁平化为 `-`。
- **对策**：对于标准规范条文（例如 `1.1`、`1.1.1`、`1.`、`(1)`），在构建下游 RAG 知识切片时，需增加基于条文编号的正则后处理，重新构建 `#`、`##`、`###` 标题层级。
- **工具**：`tools/rebuild_headings.py`。章（`1 总则`/`第一章`/`附录A`）→ `##`，节（`3.1 一般规定`）→ `###`，条文（`3.1.2 ……。`）保持段落并加粗编号；目录引导线行、代码块、表格不动。裸数字章号要求按 1、2、3 递增，避免把条文内的款项「1 电压等级」误升为章标题。

### 坑 6：统计口径的“字节”与“字数”偏差
- **现象**：终端工具 `wc -c` 统计的是 UTF-8 **字节数**而非中文汉字数。在 UTF-8 编码下每个汉字通常占 3 个字节。误将 300KB 的文件称为“30 万字”，实际可能仅有 7~8 万汉字。
- **对策**：统一使用 Unicode 范围 `\u4e00-\u9fff` 进行中文字符统计：
  ```python
  chinese_char_count = sum(1 for char in text if '\u4e00' <= char <= '\u9fff')
  ```
  生僻字（扩展 A 区 `\u3400-\u4dbf` 等）在地名、人名中并不少见，`tools/qa_check.py` 的统计已包含这些区段，并同时给出字节数、字符数与汉字数。

### 坑 7：超长文档慎用同步阻塞
- **现象**：长达几百页的扫描件一次性扔给后台解析，由于网络抖动或超时，客户端直接断连，不知道处理到哪一页。
- **对策**：
  1. 采用「拆分 PDF -> 分批执行 -> 汇聚合并」流程；
  2. 每一批保持独立的任务状态记账（state.json），支持断点续跑。

### 坑 8：绝不把 Hybrid 当做有文本层 PDF 的升级项
- **现象**：总以为“Hybrid（混合提取）既有文本又有 OCR，肯定比单纯纯文本提取更好”。
- **实测结果**：在原有纯净文本层上叠加 OCR，很容易导致原本规范中的英文缩写、符号产生乱码和幻觉。有文本层就走单纯流式提取，无文本层才走 OCR。

### 坑 9：本地版面模型冷启动等待
- **现象**：使用本地重型模型（如 MinerU managed 服务）时，服务进程刚拉起就立即发送请求，报错不可用。
- **经验**：本地多模态模型加载权重需 15~30 秒，启动后应循环探测健康探针（health check），确认就绪后再喂入文档。

### 坑 10：大批量图纸串行处理优于激进并发
- **经验**：工程图纸分辨率高、版面复杂，并发多进程容易迅速耗尽本机 GPU 显存或引发 CPU 节流。保持单队列稳健串行，并对已完成图纸打标跳过，能保证长批次任务无看护平稳跑完。

### 坑 11：归档与数据资产规范
- **经验**：转换产出的 Markdown 成果建议连同原文件名、转换引擎信息、抽取时间一并写入 Frontmatter 元数据中，保持工程文件资产溯源性。
- **工具**：`tools/add_frontmatter.py` 写入 `source_file`、`source_sha256`（判断原件是否被替换）、`source_pages`、`engine`、`document_type`、`converted_at`、`chinese_chars`；已有 Frontmatter 中的其他字段（如 Obsidian 的 `tags`）原样保留，可重复运行。

### 坑 12：敏感涉密文件坚守本地离线通道
- **底线**：涉及核心工程机密、未公开图纸、涉密技术规格书，严禁提交到外部公网 API。本地部署 basic 档或轻量开源工具完全满足离线处理需求。

### 坑 13：有字 ≠ 有文本层——乱码文本层
- **现象**：PDF 每页都能抽出上千字符，但内容是 `■■■`、`□□□`、`�`、私用区字符或 `(cid:123)`。常见于字体未嵌入或缺少 ToUnicode 映射的老版本出版物、CAD 导出图纸。按字符数判断会走 fast 模式，产出整本乱码。
- **对策**：统计乱码字符占比，超过 20% 的页面按图像处理，走 OCR。`classify.py` 将其判为 `garbled`。

### 坑 14：只看前几页会误判
- **现象**：封面、扉页、目录几乎没有正文，前 5 页平均字符数很低，整本电子版规范被误判为扫描件；反之，后半本才出现的扫描附录（盖章批复、会签页）被完全漏掉。
- **对策**：在全文范围内均匀采样（首末页必含），短文档直接逐页全量扫描；发现页面类型不一致时按页段拆分路由，而不是整本选一个引擎。

### 坑 15：扫描件自带 OCR 层与整页背景图
- **现象 1**：从标准馆、文库下载的扫描版规范常自带一层**隐形 OCR 文字**（渲染模式 3），抽取能拿到文字，但质量远不如原生文本层，形近字、错行较多。
- **现象 2**：反过来，一些电子版文件为了加水印或边框，整页铺了一张背景图，图片覆盖率接近 100%，但文字是正常可见的原生文本。
- **对策**：同时看图片覆盖率与隐形文本占比：图片覆盖高 + 文字隐形 → `scan_ocr_layer`，正式入库必须重新识别（见坑 16）；图片覆盖高 + 文字可见且每页不同 → 仍按文本页处理；文字可见但每页相同 → 是水印，按扫描页处理（见坑 18）。


### 坑 16：扫描件自带的 OCR 层，错误恰好集中在最要命的字段
- **现象**：一本 99 页的扫描版国家通用规范，自带隐形 OCR 层。逐行对照原图抽查 2 页（约 1,166 个汉字）：正文汉字只错 4 处（约 0.3%），看上去"质量不错"；但抽到的 2 处条文编号、2 处尺寸数值、3 处标准编号**全部有错**：`3.2.11` 成了 `3.2.n`，`3.2.10` 被拆成两段，`周围 2m` 成了 `周围Zm`，`10m` 丢了 `1`，`CJ 94` 的两个数字顺序颠倒，`521-2018` 的连字符成了汉字「一」，同一文档里同一个标准号一处对、一处错。
- **为什么危险**：`3.2.n` 和 `3.2.11` 通读时极易漏过；编号错了条文无法引用，尺寸错了规定失效，标准号错了指向另一份文件。抽检发现不了，同文档内连"格式自洽"都不成立。
- **对策**：`scan_ocr_layer` 一律重新识别，不要直取。同两页交给 MinerU（vlm 模型）重新识别，8 处错误全部正确；整本 99 页重新识别后，条文编号完整连续。
- **注意判断依据**：不要用"高频字表命中率"之类的统计去评估 OCR 层质量——规范里的「贮、罐、隙、渗、阀、膨胀」和前言里的起草人姓名都是低频字，却不是错字。要渲染原页逐字对照，并且专门看编号、数值、标准号。

### 坑 17：重新识别时必须强制 OCR，并用旧层错字反向验证
- **现象**：带文字层的 PDF 交给 MinerU 等引擎时，默认的自动模式可能判断"已有文字层"而沿用它，坑 16 的错字原样回到结果里。
- **对策**：
  1. 强制 OCR：云 API 设 `is_ocr: true`，本地 CLI 用 OCR 方法（参数名以所用版本的文档为准）。`tools/mineru_cloud.py --ocr auto` 在 classify 发现 `scan_ocr_layer` 或 `garbled` 页时自动打开。
  2. 反向验证：把坑 16 里核实过的旧层错字列为禁用串，结果里出现任何一个，说明沿用了旧层：`qa_check.py --forbid "3.2.n" --forbid "Zm内"`（`mineru_cloud.py` 同样支持 `--forbid`）。
  3. 完整性：`qa_check.py --clauses` 检查条文编号在每节内是否从 1 起连续；`mineru_cloud.py` 还会把每页识别出的汉字数与原文字层比对（旧 OCR 层正文汉字基本准确，适合当字数基准），比值低于 0.8 或高于 1.2 的页列出来，多为漏段或串页。

### 坑 18：扫描件上的"可见水印"伪装成文本层
- **现象**：从资料站下载的扫描版教材，每页压着一两行可见文字（站名、网址、"仅供学习"），约 90 个字符，越过了"有效文本"门槛，且不是隐形文字。只看字符数和渲染模式，整本会被判为文本页送去 fast 抽取，产出只有几百行一模一样的水印。
- **对策**：统计跨页重复行。整页图 + 去掉重复行后几乎无字 → 扫描页。`classify.py` 已内置（`WATERMARK_REPEAT`，至少 3 个采样页时生效）。

### 坑 19：Windows 中文环境下调用外部命令的编码
- **现象**：`subprocess.run(["where", "mineru"], text=True)` 报 `UnicodeDecodeError: 'utf-8' codec can't decode byte 0xd0`。更隐蔽的是异常发生在读取输出的线程里，主流程照常往下走，结果被误判成"没装"。
- **根因**：Python 处于 UTF-8 模式（设置了 `PYTHONUTF8=1`，很多 Agent 运行环境默认如此）时，`text=True` 按 UTF-8 解码；而 Windows 原生命令按系统代码页（中文系统为 GBK/cp936）输出。不在 UTF-8 模式时则按 cp936 解码，同一段代码换个环境变量就表现不同。
- **对策**：
  - 判断命令是否存在一律用 `shutil.which()`，完全不经过子进程；
  - 必须读取原生命令输出时，取字节再自行解码（`tools/_compat.py` 的 `run_text()`：先试 UTF-8，再用系统代码页）；不要用 `encoding="utf-8", errors="replace"`——它把中文路径静默变成乱码，比报错更危险；
  - 不能把"没拿到输出"当成"没安装"，要显式检查退出码和输出内容；
  - 输出重定向到文件时，中文 Windows 默认按 GBK 写出，下游按 UTF-8 读就是乱码。本项目所有工具在非交互输出时统一改为 UTF-8。

### 坑 20：大幅面图纸的矢量计数很慢
- **现象**：A3~A0 施工图单页可达数十万条矢量路径，逐条统计（PyMuPDF `get_cdrawings`）要 1.5~4 秒/页，一套 46 页图纸光分类就要几分钟。
- **对策**：用页面内容流字节数代替。实测 46 页施工图字节数与路径数 Spearman ρ=0.979、Pearson r=0.987，读取快约 20 倍。但字节数**不能单独**当图纸判据：图文混排书籍的插图页最高约 30.7 万字节，而图纸页最低约 34.6 万字节，只差 13%。必须与图幅（长边 ≥415mm）同时使用。

### 坑 21：视觉模型兜底，上线前先用已知答案的样本实测
- **现象**：某内网部署的多模态端点，对一张 2000×358 像素的工程图截图做 4 次识别，3 次 120 秒超时（缩小到 1000×179 仍超时），唯一一次返回漏掉了 3 行图名中的 1 行。
- **对策**：
  - 用"标准答案已知"的区域测试：选图片区域内同时有原生文字层的页面，用文字层当答案；
  - 注意答案的覆盖范围：原生文字层只覆盖叠加在图上的文字，位图本身画出来的标注不在其中。模型"多输出"的内容可能是图里真实存在的字，不能直接判为编造，要人工核对；
  - 超时率高或漏字的端点不要写进自动流程；视觉模型的输出未经人工复核不得进入成果文件。

### 坑 22：页内大图里的字，fast 模式抽不到
- **现象**：PPT 导出的汇报材料、图文混排书籍里，标题和说明是原生文字，表格、平面图、效果图却是截图。整页送 OCR 浪费且可能把原生文字识别错；只做 fast 抽取又会整块漏掉图里的信息。
- **对策**：页按 `text` 处理，大图单独处理。`classify.py` 在 `pages[].figures` 给出每张 ≥15% 页面的图片外接框，按框以 2 倍分辨率裁图后识别，结果按 `y0` 插回该页正文。封面、PPT 全屏背景页同样适用。

### 坑 23：云 API 的边界要写成规则，不能靠"判断内容是否涉密"
- **现象**：云 OCR 跑通之后，最容易发生的是顺手把项目图纸、汇报材料也传上去。让程序或 Agent 去"判断这份文件是否涉密"是不可靠的。
- **对策**：按目录白名单决定能否上传。`tools/mineru_cloud.py` 只上传配置 `cloud_allowed_dirs` 里的文件（规范库、公开出版物等），未配置白名单时一律拒绝；白名单外的文件必须由人显式加 `--allow-outside-whitelist`。也要清楚：Agent 读过的任何内容本身就会发给它背后的模型服务，白名单管住的只是"不再额外交给第三方 OCR 服务"。
- **token 存放**：放在系统钥匙串（macOS Keychain、Windows 凭据管理器、Linux Secret Service，经 `keyring` 库统一读取）或环境变量里，不写进配置文件、脚本、日志和聊天记录；曾在聊天里明文出现过的 token 立即作废重建。
