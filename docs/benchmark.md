# 实测基准数据 (Benchmark)

本基准数据基于对中文工程标准规范文档（真实工程规程样本，42MB，200 页）在 macOS 环境下的实测记录。

---

## 1. 性能对比摘要

| 指标 | 方案 A：OpenDataLoader PDF (Fast 模式) | 方案 B：传统版面 OCR 引擎 / 多模态云端 | 差异幅度 |
|---|---|---|---|
| **处理总耗时** | **1.12 秒** (秒级瞬发) | 120 秒 ~ 600 秒 (视排队与并发而定) | **提速 100x+** |
| **产出文本量** | 145,321 字符 (约 77,200 汉字) | 约 76,000 ~ 77,500 汉字 | 相当 |
| **条文读序还原** | 严格符合左至右、章节递进顺序 | 偶有分栏跨栏串读 | Fast 表现更优 |
| **专有名词准确率** | **100% 原始文本还原**（零字符幻觉） | ~98.5%（偶发形近字识别错误） | Fast 零损耗 |
| **资源消耗** | 极低（纯 CPU 单线程流式解析） | 需 GPU / 显存 或高带宽上传 | Fast 极度轻量 |

### 1.1 MinerU 云 API：整本提交 vs 逐页提交（Windows，2026-11）

| 样本 | 提交方式 | 参数 | 耗时 | 额度 |
|---|---|---|---|---|
| 扫描版国家通用规范，99 页，59.6MB，整页图 + 隐形 OCR 层 | 整本一次 | `model_version=vlm`、`is_ocr=true` | **110 秒**（含上传、排队约 15 秒、解析约 76 秒、下载） | 99 页 |
| 同一文件抽出的单页 | 每页一次 | 同上 | 每页约 2.5 分钟（以排队为主） | 1 页/次 |

质量：旧 OCR 层在抽查页中的 8 处错误（条文编号、尺寸、标准号）全部被正确识别；整本结果中 4 个已知错字一个未出现，
条文编号 351 条连续。结论：云 API 一律整本或按页段一次提交。

## 2. 结论与工程指导

1. **有文本层文档（电子版规程、说明书）**：
   - 坚决走纯文本流式抽取。
   - 不仅在耗时上带来数量级的飞跃，更重要的是**根除了 OCR 对工程数字与英文代号的误识别**风险。
2. **纯扫描件与图像型 PDF**：
   - Fast 模式无效（输出 0 字节），此时必须无缝回退到版面识别模型（MinerU 等）。

## 3. 补充基准数据的建议格式

欢迎用自己的样本补充数据。为了让数字可比，请同时记录：

- 硬件与系统（CPU 型号 / 内存 / GPU，macOS 或 Linux 版本）；
- 引擎版本（`opendataloader-pdf` 版本与 Java 版本、MinerU 版本与 tier）；
- 样本特征：页数、文件大小、`classify.py` 的 `document_type` 与 `page_classes`；
- 准确率口径：建议以 fast 抽取结果为参照，用 `tools/qa_check.py ocr.md --against fast.md` 统计数字缺失/多出个数，代替主观的"准确率百分比"。
